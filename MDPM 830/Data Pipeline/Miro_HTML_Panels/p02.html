Scope boundary: the Furniture Request journey
Sinks (Step Three)
1 · Generatesomeone or something creates data as work happens
2 · Collectit gets captured, under someone's permission
3 · Keep and Shapethe original is kept; a consistent, trusted version is made
4 · Storeit lives somewhere more than one consumer can reach
5 · Usea feature, a model, a report, a decision
Sinkswhere data stops moving and creates value
Responsible: each creator, for what they state
  • Original requester person
  • CMAC person
  • Furniture Request Coordinator (FRC) staff
  • Furniture Coordinator (FC) staff
  • Vendor or supplier third party
  • PRISM Requests system, proposed
Passes on: request details, documents, decisions, updates
Responsible: CMAC, for the details submitted (Proposed); staff, for email and vendor information they capture
  • Guided form: fields, checklist, attachments
  • Case activity: FRC and FC decisions, status changes, messages
  • Vendor correspondence, captured by staff
Passes on: the request exactly as submitted
Responsible: Open (Proposed: FRC)
  • Keep the original as submitted
  • Check completeness by request type
  • Link every update to one Request ID, one status, a named owner
  • Prepare consistent reporting fields
Incomplete: returned to the CMAC, then checked again
Passes on: one trusted request record
Responsible: data owner, Open
One shared request record, keyed by Request ID
  • Request and contact data
  • Status history, assignment, ownership
  • Documents and completion records
  • Timestamps and audit history
The original is never overwritten
Passes on: authorized case data
Responsible: data owner, for what views show; report owners Open
  • Request views for CMACs and coordinators
  • Outcome measures for evaluators
  • Operational reports for Infrastructure management
Passes on: each use to its sink
