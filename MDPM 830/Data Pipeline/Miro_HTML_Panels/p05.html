Responsibility, preparation and constraints

5 / 12

Entering data is not the same as being accountable for it. Creators answer for what they state. The stage owner answers for the rules that make the data trusted. The data owner answers for the request record from start to finish.

What clean and trusted means here

Keep and Shape. Proposed rules, to confirm with the business.
  1. One Request ID, with every material update linked to it
  2. One status from an agreed list, with a defined meaning
  3. A named owner at every stage
  4. Required fields and documents complete before review
  5. Dates in one format and in true order
  6. Duplicate requests checked on an agreed match key

A request that fails the checks goes back to the CMAC and is checked again. The prototype shows why the rules matter: one request appears as both "Awaiting initial review" and "Reviewing", and some activity is dated before submission. We state what preparation must achieve, not how it is engineered.

Constraints

Quality
Floor plans may not be current; submission materials may be missing; status meanings and completion criteria not yet confirmed; no agreed match key for duplicates.
Frequency
Requests are created by people, intermittently, one at a time. Updates are event-driven, at each decision or status change.
Format
Needs arrive by email, Teams and phone. Attachments include floor plans and PDFs. The prototype limits uploads to 10MB per file and 5MB per reply.
Ownership
Keep and Shape owner: Open (Proposed: Furniture Request Coordinator). Data owner for the request record: Open.
Access
Who may view, update or share each item is to be confirmed. Proposed: a CMAC sees only their own requests.
Retention
Requirements to confirm. Historical WORTS migration is an open decision.
